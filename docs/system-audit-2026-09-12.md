## 重复与冗余检查

- 对后端函数体做 AST 完全重复扫描。发现 `count_pending_keyword_enrichment` 与 `count_unchecked_keyword_enrichment` 查询完全相同；后者保留兼容入口，委托前者执行。
- ManagedLLM 的分析/聊天重复请求与用量统计已合并为文本请求和流式请求两条公共实现，并统一关闭网络连接。
- 公开论文和私人文库不再分别传入固定输出 token 参数，避免同一策略多处维护；删除失去用途的输出常量。
- 标题修复复用受保护片段处理，不再为 Zotero 单独维护只识别三反引号的代码围栏状态机。
- 前后端 Markdown 处理仍各有实现：后端保证保存与导出可用，前端兼容历史内容与流式展示。这不是可直接删除的重复，已用相同边界情形做回归测试。
- 路由入口 JS 从本轮前的约 1,464 KB 降至约 305 KB（未 gzip）。这是入口文件大小，不是所有页面资源合计，也不代表实测网络延迟下降同样比例。管理图表和公式渲染分块按需加载。
- `outputs/` 为用户已有的未跟踪产物，本轮未修改；已排除出 Docker 构建上下文，避免无关分析产物随镜像打包。

## max tokens 的实际含义

管理后台“深入解读输出额度”保存到供应商私有参数 `_analysis_max_tokens`，不会透传私有参数给模型。

- 不传该字段：保留原供应商设置及兼容默认值。
- 正整数：分析使用此额度；不会同时发送互相冲突的 `max_tokens` 与 `max_completion_tokens`。
- 明确设为 null（界面清空并保存）：OpenAI 兼容接口不额外设置分析输出上限，但供应商默认值和模型上下文/输出硬上限仍然存在。
- Anthropic Messages 的 `max_tokens` 是必填参数，应用自动模式使用 32,768；如具体模型不支持此额度，需要设置其支持的正整数值。
- 不改变聊天/笔记额度。GLM 代理的长文输入筛选与输出额度是两回事，不能把选取的主文片段称为无损全文。

API 参数参考：[Claude Messages](https://platform.claude.com/docs/en/api/messages/create)。Zotero 数学节点参考：[官方 note-editor schema](https://github.com/zotero/note-editor/blob/master/src/core/schema/nodes.js)。

## 尚需单独处理的结构性事项

- `app.py` 与 `database.py` 仍是大文件，路由和数据访问职责较集中；适合后续按认证、论文、Zotero、模型管理拆分，不能靠删行数来代替行为验证。
- 长报告任务目前依赖 SSE 请求生命周期。主报告完成前离开页面仍可能取消生成；要真正做到断线后继续运行，需要持久化任务队列与任务状态接口。
- 已增加生成笔记保存时的数据库级 CAS，以及写回前的报告哈希检查；完整的跨窗口任务去重、同一报告多次写回的幂等仍需单独处理，不能把 CAS 等同于完整任务调度。
- 本轮没有引入新的云存储后端、生产数据库迁移或全量重生成旧报告，也没有宣称不存在其他 bug。
